## 1. 진행 방법

PRD의 각 기능을 본체에 통합하기 전에 **작은 검증 프로그램(spikes/)**으로 PRD 임계값을 기계 측정한 뒤 구현했습니다. 구현 후 단위·통합 테스트 67건과 실제 브라우저(Microsoft Edge) + 실제 Azure E2E(`ui/e2e.mjs` 9항목, v1.1은 `ui/e2e-v11.mjs` 29항목)로 확인했습니다.

| spike | 검증 내용 | 결과 | 발견 사항 → 설계 반영 |
|---|---|---|---|
| [01-ingest](../../../spikes/01-ingest.cs) | ffprobe·VFR·회전·잘못된 파일·CFR 프록시 | 모두 통과 | MKV 메타데이터에는 VFR이 보이지 않음 → **패킷 시각 차이로 VFR 판정** |
| [02-signals](../../../spikes/02-signals.cs) | 숏 경계(scdet)·100ms 음량·무음·피크 | 모두 통과(정답 대비 ±0.1초) | PySceneDetect 대신 FFmpeg 기본 scdet로 충분(PRD D-4 대안) |
| [03-render](../../../spikes/03-render.cs) | ASS·흐린 배경·펀치인·음량·결정성·세로 원본 | 모두 통과 | ①`cropdetect`의 잘못된 통과 → **원시 픽셀에서 문자 외접 사각형 직접 측정** ②1패스 loudnorm은 −17.3 LUFS, 2패스 linear도 조용히 dynamic으로 돌아가 −15.1 → **내보낸 뒤 측정하여 음성만 보정하는 루프** |

이 절의 테스트 원본은 권리 문제를 피하려고 모두 합성(FFmpeg 테스트 패턴 + Azure TTS 음성)했습니다. §2.2 AT-10 재검증만 사용자가 지정하고 외부 전송을 허가한 실제 영상을 사용했습니다. §2.3은 고정 전사·FFmpeg 합성 미디어이며 실제 Azure로 전송하지 않았습니다.

### 2.2 AT-10 실제 통신 검증

2026-11-08, 명시적인 전송 허가를 받아 지정 MOV 전체에서 **P4 생성을 양 모드 모두 완료**했습니다. 실행한 Azure CLI 인증 구성에서 **AT-10 통과**입니다.

- 입력: `20260615_024326000_iOS.MOV`, 1081.42초(약 18분 01초), 6,494,572,403 bytes, 3840×2160 HEVC / AAC 48kHz stereo.
- 입력 SHA-256: `fe9c763fdf6fe7be4f368bfba926a1f3f2407ceaf044ec7d055e0869e65c1a9f`. 양 프로젝트 등록 결과 일치.
- 프로젝트·데이터·ASR 캐시를 모드별 분리. 로컬 생성 `proxy.mp4`·`audio16k.flac`만 재사용하며 전사는 복사하지 않고 각 모드에서 ASR을 새로 호출. 각 음성 multipart POST 36,502,012 bytes.
- 생성 조건: P4, balanced, BGM 없음, SFX/반응/오프닝/클로징 없음. 모델은 일반 모드만 `gpt-chat-latest`. 본 내보내기는 범위 밖.

**관측 방법과 실패 취급**

ASR·LLM이 같은 Azure 호스트를 사용하므로 IP·호스트명만으로 구분할 수 없습니다. 모드별 루프백 HTTPS 프록시에서 TLS를 일시 종료하여 `POST /speechtotext/transcriptions:transcribe`·`POST /openai/v1/chat/completions`를 구분했습니다. 기록은 시각·대상·메서드·경로(쿼리 제외)·응답 코드·바이트 수뿐입니다. 인증 헤더·음성·전사·LLM 응답 본문은 프록시 로그에 저장하지 않았습니다. 상위 TLS 인증서 검증은 유지했으며 영상 프레임은 전송하지 않았습니다.

첫 LLM 미사용 실행에서 Azure CLI 인증 자식 프로세스가 `dc.services.visualstudio.com` 텔레메트리 접속을 시도했습니다. 프록시가 차단해도 **AT-10 실패**로 기록하고 통과 증거에서 제외했습니다. [Runtime.cs](../../../src/VideoCreator.App/Runtime.cs)에서 `AZURE_CORE_COLLECT_TELEMETRY=false`를 앱 자체 프로세스 환경에 설정해 인증 자식 프로세스가 상속하게 했습니다. 사용자 전역 Azure CLI 설정은 바꾸지 않았습니다. [PrdVerificationTests.cs](../../../tests/VideoCreator.Tests/PrdVerificationTests.cs) 관련 4건 통과 후 양 모드를 재실행하여 위 결과를 얻었습니다.

프록시 기록 외에 .NET 소켓 연결 이벤트·앱/하위 프로세스 IPv4/IPv6 TCP 표를 감시했습니다. FFmpeg 자식 검출·앱 종료까지 감시를 확인했습니다. TCP 표 표본은 LLM 미사용 11,439개, 일반 27,172개. 설정 간격 20ms이나 실제 최대 간격은 484ms·500ms입니다. **표본 추출만으로 짧은 네이티브 접속을 모두 부정할 수 없습니다**. 전체 OS 통신 패킷 캡처·모든 인증 방식 증명과 구분하고 프록시·.NET 이벤트를 주된 증거로 사용합니다. 토큰은 Azure CLI 캐시를 사용하여 이번 기록에는 Entra ID HTTP 요청이 없습니다.

원시 기록은 이 검증 세션 `files\at10`에 보관했습니다. `at10-summary.json`에 판정·작업 ID·입력 해시·관측 조건·원시 기록 SHA-256, `validate-evidence.py`에 기계 판정, 모드별 JSONL에 통신·소켓 원시 기록, `preflight.json`·화면 이미지에 생성 전 표시, `result.json`에 생성 완료를 저장했습니다. 최초 텔레메트리 실패 기록도 남겼습니다. 비공개 원본·전사·화면 이미지는 저장소에 복사하지 않았습니다. 검증 앱·감시·프록시를 종료하고 임시 CurrentUser Root 인증서·개인 키 파일 삭제를 확인했습니다.

이는 **원본 1개·P4·이번 Azure CLI 인증 경로**의 AT-10 증거입니다. 18분 영상을 TC-JA-60 지정 실제 대담이나 사람 정답 10원본의 대용으로 삼지 않으며 AT-01·H-11·AT-13~AT-15·품질 게이트 판정은 바꾸지 않았습니다.

- 보수적인 구절 일치이며 모든 의미 변환·부정·고유 명사 검출을 보장하지 않음. 사전에 없는 한자 고유 명사 등을 포괄적으로 식별하지 않음. 정확한 바꿔쓰기 과잉 거부는 원발화에 가까운 표현·근거 재지정으로 해결. 승인으로 H-11을 우회하지 않음.
- 생성 후 실제 길이·솔버 이후 중복을 검사. 중복 티저·본문 구간은 집합으로 취급해 같은 원본으로 후보 수를 부풀리지 않음.
- 승인·검사·큐 예약·마지막 저장을 [Store.Atomic](../../../src/VideoCreator.Core/Storage/Store.cs)으로 보호. 본 파일은 출력 ID별 디렉터리에 저장해 과거 출력을 덮어쓰지 않음. 무효 산출물은 `rejected`로 격리하여 배포하지 않음.
- 과거 본 출력은 삭제하지 않으나 현재 해시와 연결된 H-11 통과가 없는 구 결과는 재승인·재QA·재출력 필요. 이전 미리 보기는 경고와 함께 열람 가능. 이전 QA를 새 계획의 통과 증거로 바꾸지 않음.
- 전사 수정도 관련 계획 해시를 무효화. 같은 원본 해시 캐시를 쓰는 다른 프로젝트도 포함하며 해당 계획 출력 중이면 거부. 구 출력이 남아 있어도 최신 유효 본 출력을 무효로 오표시하지 않음.
- 기존 화자/카메라 일치·YouTube 챕터 검사를 S-13/S-14로 바꿔 S-09/S-10과 구분. 공동 작업에서 별도 삭제된 외부 음성 이벤트 검출기는 복원하지 않고 파이프라인 참조만 제거해 기존 로컬 웃음 검출 유지.

## 10. 오프닝·클로징·장면 전환의 반응 카드

채널 오프닝/클로징과 영상을 잠시 멈추듯 삽입하는 2~3초(기본 2.5초) 반응 카드를 넣습니다. 구현: [Packaging.cs](../../../src/VideoCreator.Core/Planning/Packaging.cs)(매핑·등록·배치), [Renderer.cs](../../../src/VideoCreator.Core/Rendering/Renderer.cs), 검증: [PackagingTests.cs](../../../tests/VideoCreator.Tests/PackagingTests.cs).

P3 AI 반응 방식은 생성 시 `tsukkomi_style`로 선택합니다. `telop`은 영상을 멈추지 않는 빨간 바탕 겹침 텔롭, `card`는 발언 직후 정지 카드, `auto`가 기본입니다. `auto`는 [TsukkomiPlacement](../../../src/VideoCreator.Core/Planning/Packaging.cs)가 하나씩 결정합니다. 멈춰도 내용이 끊기지 않는 곳만 카드로 합니다. ①본편 끝에서 3초 이상 ②대상 자막이 완결·질문으로 끝남(`SplitCues.Closure` ≥ 0.6, 「〜けど」「これ」로 끝나는 발언 중간은 멈추지 않음) ③다음 자막이 응답·접속 아님(「そうそう」「だから」 등 `SplitCues.Continuation` ≤ −0.6 제외) ④전환 카드·오프닝·다른 반응 카드와 8초 이상(전환 카드와 동일 간격) ⑤합계 카드 시간이 본편 10% 이내. ②③ 만족 후보를 「완결 + 다음 발언까지 쉼(최대 1초)」 내림차순으로 ④⑤ 선택, 탈락 후보는 버리지 않고 겹침 텔롭으로 합니다. 이유를 후보 메모에 남깁니다. 검증: [PackagingTests.cs](../../../tests/VideoCreator.Tests/PackagingTests.cs) 규칙별 반례, [V11Tests.cs](../../../tests/VideoCreator.Tests/V11Tests.cs) 3모드 생성·승인 게이트, [ProjectGenerationSettingsTests.cs](../../../tests/VideoCreator.Tests/ProjectGenerationSettingsTests.cs) 저장.

`card`·`auto` 카드는 클립 중간이면 분할하면서 원영상·원음·카메라/화면 추적·PiP 시작점을 유지합니다. 카드 중 원음은 멈추고 독자 합성 `upbeat` BGM(본편 선택과 독립)을 짧게 페이드인/아웃합니다. 본편 BGM은 음소거해 중복 재생하지 않습니다. 등록 이미지가 있으면 위에 문자, 없으면 자체 전체 화면 배경 패널(안쪽 노란 테두리)에 문자를 팝업 표시합니다. 확인 화면 카드란에서 수정·승인합니다. 기존 계획의 겹침 자막·카드 음성은 자동 변환하지 않고 재생성부터 새 연출을 적용합니다. 과거 등록의 1초는 새 생성 시 2초로 보정합니다.

추가 검증은 이미지 유무 실제 FFmpeg 출력에서 2.5초 추가·카드 중 정지·재개 프레임과 미삽입 출력 일치·문자 픽셀·전용 BGM·원음 정지/재개를 측정합니다. 배속·다른 음성·PiP·가로/세로 추적 분할도 자동 테스트합니다. 참고 YouTube 지정 구간을 직접 시청하지 못했으므로 사용자 구성 설명에 근거하며 원이미지·음악을 복제하지 않았습니다.

### 작은 오프닝·클로징 고화질화

등록 OP/ED가 출력 1080×1920보다 작으면(예: 720×1280) 등록 시 한 번 고화질 버전을 만들어 출력에 사용합니다. 구현: [SuperResolution.cs](../../../src/VideoCreator.Core/Media/SuperResolution.cs), [Packaging.cs](../../../src/VideoCreator.Core/Planning/Packaging.cs)의 `BrandKitEnhancer`, [BrandKitWorker.cs](../../../src/VideoCreator.App/BrandKitWorker.cs). 검증: [UpscaleTests.cs](../../../tests/VideoCreator.Tests/UpscaleTests.cs), [spikes/14-upscale.cs](../../../spikes/14-upscale.cs).

**측정하여 방식을 정했습니다.** 정답이 있는 표준 초해상도 평가로 720×1280을 2/3 축소한 뒤 각 방식으로 1.5배 복원해 원본과 비교(FFmpeg libvmaf **NEG 모델**=샤프닝으로 점수가 오르지 않는 버전, XPSNR·SSIM, 압축 조건 동일).

|---|---|---|---|---|
| lanczos(기존 출력 확대) | 92.77 | 44.29 | 0.99792 | 기준 |
| lanczos + CAS 0.4(샤프닝) | 94.81 | 39.86 | 0.99575 | VMAF 상승, XPSNR −4.4 dB·원본에서 멀어짐 |

## 14. 전편·후편 분할점을 이야기 경계에 맞추기(SplitCues)

**문제**: Hub 라디오 Ep.014 실제18분2편에서 전편이 「…ぜひどっかだと思いますあともう一個なんですけどねこれちょっと」, 후편이 「ちょっと面白い感想かなと思ったんですけど、…」로 이어져 이야기 중간에 잘렸습니다.

**원인(원시 데이터)**: 문장 경계만 후보이나 Azure Fast Transcription이 「…と思います」·「あともう一個…」를 마침표 없이 한 문장으로 묶었습니다. 단어 시각상 「思います」 뒤 **0.36초 쉼**이 진짜 경계입니다. AI는 다음 「ちょっと面白い…」 행에 적합성9를 주었으며 직전 문장 완결 여부가 점수에 없어 채택했습니다. 고정 카메라라 숏 경계0·영상 단서 없음.

### 조사(YouTube / TikTok 분할)

| 출처 | 발견 | 반영 |
|---|---|---|
| 게시자 YouTube 챕터(YTSeg, EACL2024)·본 §9 | 주제 경계는 앞 이야기가 완결된 직후 | 아래 완결 판정 |
| TikTok Part1/2 안내 | 전편은 질문·전조 완성으로 끝내고 답은 후편. **전조 중간 금지** | 질문도 완결, 도중 경계 강한 감점 |
| J/L 컷(음·영상 시차) | 웃음·반응 뒤 컷, 암전·전환은 구분 신호 | 웃음 직후 가점/중간 감점·암전/숏 가점 |

### 구조([SplitCues.cs](../../../src/VideoCreator.Core/Planning/SplitCues.cs), 시리즈만)

| 단서 | 판정 | 경계 점수 |
|---|---|---|
| 누락 문장 끝 보완(`Resegment`) | 한 문장 내 왼쪽이 강한 종결(〜ます/〜です/〜ました/〜でしょう 등)·0.3초 이상 쉼인 단어 사이 분할. 단어 불변·각 단어 정확히 한 문장. 문장 표기와 단어 연결이 불일치면 그대로 | 후보 추가 |
| 앞 문장 끝(`Closure`) | 완결+1·질문+0.6·「〜けど。」 같은 미완0·쉼표/접속 조사(けど/て/で/から…)·지시어/필러(これ/ちょっと/えっと…)로 끊김−1 | +0.3×완결, **끊김−2.0**(AI 최대 가점1.6보다 큼) |
| 다음 시작(`Continuation`) | 앞말 받는「で、」「だから」「それで」「そうですね」(「はい、」「まあ」등 건너뜀)−1·지시어 시작−0.6 | ×0.8(구어 「だから」는 단순 도입도 있어 약하게) |
| 정리 표현 | 「ということで」「以上」「ありがとうございました」로 끝남 | +0.4 |
| 웃음 | 직전에 끝남 / 경계를 가로지름 | +0.3 / −0.5 |
| 영상 | 암전(`blackdetect=d=0.2:pix_th=0.10`, scdet와 같은 디코드) / 숏 경계 | +0.8 / +0.4 |

AI 프롬프트도 「직전 행이 완결·질문이며 다음 행이 앞말을 받지 않는 위치만 높은 적합성」으로 명시(`series-1.1.0`). 허용 길이 안에 완결 경계가 없으면 어떤 파트가 도중에 끝났는지 경고합니다. 설명은 「문장 완결」「영상 암전」「웃음 직후」 등의 근거입니다. 캐시를 `signals.v2.json`으로 변경하여 다음 생성에서 암전 자동 재분석(18분에서 약+2초).

## 15. 분할점은 장면(주제) 경계로만 결정(장면 우선)

§14까지는 길이 균등을 우선하고 허용 범위에 주제 경계가 없으면 언어상 끊기 좋은 곳을 택했습니다(전반7분 Azure·후반3분 Copilot을5분 근처에서 분할). 세 가지를 변경했습니다.

1. **장면 우선**([Series.cs](../../../src/VideoCreator.Core/Planning/Series.cs) `SceneStrength` / `Split`): 어휘 변화·전환어·AI 챕터 시작·암전만으로 경계 증거를 만들고 **장면 경계만 후보**로 먼저 분할합니다. 길이 추정의30~170% 허용, 단 편당60초 이상. ±25% 초과 경고. 쉼·완결·웃음·컷은 위치 채점에만 사용·장면 증거 제외. 경계 부족일 때만 기존 길이 우선·「주제 도중 분할」 경고.
2. **의미로 주제 판단**([TopicEmbedding.cs](../../../src/VideoCreator.Core/Planning/TopicEmbedding.cs)): 기존 Microsoft Foundry `text-embedding-3-large` 문장 벡터의 앞뒤30/60/90초 평균 골(TextTiling)을 어휘 골과0.7:0.3 혼합(`Llm.EmbeddingDeployment` 비거나 오프라인이면 어휘만). 어휘만으로는 바꿔말하기·ASR 변동이 같은 주제를 갈라놓고 공통어가 다른 주제 골을 얕게 합니다. `cache/<원본>/topic_embed.json` 저장(18분1엔 미만). 기존 Foundry만 전송, `provider=none`·`LocalOnly`에서 미사용.
3. **어휘 골 다중 창**:45초 단일 창은 적은 단어 우연 골이 있어30/60/90초 평균으로 변경.

## 16. 한 프로젝트에 여러 패턴(Job)을 남기고 이전 단계부터 다시 하기

## 18. 한 패턴의 여러 영상을 개별 확인·일괄 출력

한 Job에서 후보·시리즈 여러 편을 만듭니다. 「5 확인·수정」을 각 영상에 수행하고 승인본을 「6 내보내기」에서 일괄 출력합니다. 승인 해시 결합·`POST /api/jobs/{id}/exports` 전체 사전 검증(하나라도 불가하면 아무것도 시작 안 함)은 유지하고 UI 흐름만 추가했습니다.

- 확인 순서: 제목 아래 이전/다음/상태 포함 선택. 주 버튼 「승인하고 다음 영상으로(이름)」은 다음 미승인으로(끝이면 처음부터·현재 제외). 승인 직후 목록 재조회로 결정하여 다른 화면에서 승인되어도 승인본에 돌아가지 않음. 나머지 전부 승인되면 「승인하고 내보내기」. 현재 이미 승인되면 기록 중복 없음. 하드 실패면 모든 승인 비활성.1편이면 기존 「이 내용 승인하고 출력」.

## 20. UI·문서·동영상의 다국어 지원

- UI는 일본어·영어·중국어(간체)·한국어를 지원하며 표시 언어와 동영상 언어를 분리합니다. 원문과 같은 구조의 번역 문서를 `locales/en` / `locales/zh-CN` / `locales/ko`에 배치합니다. 과거 일본어 스크린샷은 촬영 당시 실제 화면이며 번역 UI의 증거가 아닙니다.
- 프로젝트 `language`는 `ja-JP`(기본값) / `en-US` / `zh-CN` / `ko-KR`입니다. 생성·변경 API에서 검증하고 생성·내보내기 중 변경을 거부합니다. `Runtime.AsrForLanguage`에서 Speech의 `locales`로 전달합니다. 전사·웃음 검출 캐시를 언어별로 분리하고 과거 계획 QA·재편집·게시 문장은 계획 언어의 전사를 읽습니다.
- 자막은 발화 그대로입니다. 영어·한국어는 ASR 단어 사이 공백을 복원하고 일본어·중국어는 문자를 연결합니다. `CaptionText`가 언어별 분할·개행·정규화를 수행합니다. QA 복구도 같은 연결법으로 단어·ID·시각 대응을 유지합니다. 여러 단어에 걸친 가림말도 공백을 포함하여 검사합니다.
- 선정·시리즈 챕터·연출 텔롭·카드·QA AI 복구·게시 문장 프롬프트에 동영상 언어를 지정합니다. 정형 카드·효과 문자·시리즈 복습/예고·게시 템플릿도 같은 언어로 출력합니다. AI 연출 변경은 기존처럼 미승인 상태로 만들어 사람 확인을 요구합니다.
- `EditPlan.language`에 생성 당시 언어를 저장합니다. 일본어·영어는 M PLUS 1p, 중국어는 Noto Sans CJK SC, 한국어는 Noto Sans CJK KR을 사용합니다. `scripts/get-tools.ps1`이 OFL 폰트·라이선스를 받습니다. 필요한 CJK 폰트가 없으면 명시적으로 내보내기를 실패시키며 OS 대체 폰트에 의존하지 않습니다.
- [LocalizationTests.cs](../../../tests/VideoCreator.Tests/LocalizationTests.cs)로 API 영속성/잘못된 값·Speech 요청 언어·언어별 캐시·단어/공백/가림말 보존·AI 프롬프트·ASS/SRT·libass 실제 렌더링/글리프 누락·긴 영어·중국어·한국어 자막의 안전 영역 픽셀 실측·MP4 미리 보기를 검증합니다. 일본어 이외 언어의 폭 추정에서는 폭이 넓은 라틴 문자도 고려하며, 렌더링과 얼굴 회피 배치가 같은 폰트 크기 조정 방식을 사용합니다. 문서 구조·범위·링크는 `node scripts/verify-localized-docs.mjs`로 검사합니다.
- 제약: 자동 테스트는 합성 영상·음성·고정 응답을 사용합니다. 영어·중국어·한국어 실제 발화의 Speech 인식 정확도·AI 문안 자연스러움·원어민 번역 교열을 보장하지 않습니다. 자막 자동 번역·여러 음성 언어가 섞인 영상의 자동 언어 판정은 범위 밖입니다.
