# VideoCreator 実装・検証レポート

- 対象: [PRD.md](PRD.md)（VC-PRD-001 v1.0）
- 日付: 2026-11-07
- 実装: C# / .NET 10（ASP.NET Core Minimal API、ローカル Web アプリ）＋ Fluent 2 Web Components v3
- 検証環境: Windows 11 ARM64、FFmpeg N-128532（BtbN win-arm64 GPL）、Azure（Japan East）

## 1. 進め方

PRD の各機能について、本体に組み込む前に **小さな検証プログラム（spikes/）** を作り、PRD の閾値を機械計測で確認してから実装しました。実装後は単体・結合テスト（67件）と、実ブラウザ（Microsoft Edge）＋実 Azure を使った E2E（`ui/e2e.mjs` 9項目、v1.1 は `ui/e2e-v11.mjs` 29項目）で確認しています。

| spike | 検証内容 | 結果 | そこで見つかったこと → 設計への反映 |
|---|---|---|---|
| [01-ingest](../spikes/01-ingest.cs) | ffprobe・VFR・回転・不正ファイル・CFR プロキシ | 全合格 | MKV はメタデータ上 VFR が見えない → **パケット時刻の差分で VFR を判定** |
| [02-signals](../spikes/02-signals.cs) | ショット境界（scdet）・100ms 音量・無音・ピーク | 全合格（正解との差 ±0.1秒） | PySceneDetect の代わりに FFmpeg 標準の scdet で十分（PRD D-4 の代替案） |
| [03-render](../spikes/03-render.cs) | ASS・ぼかし背景・パンチイン・音量・決定性・縦型素材 | 全合格 | ①`cropdetect` は誤合格を出す → **生画素から文字の外接矩形を自前で計測**　②1パス loudnorm は −17.3 LUFS、2パス linear も黙って dynamic に戻り −15.1 → **書き出し後に測定して音声だけ補正するループ** |
| [04-asr](../spikes/04-asr.cs) | Fast Transcription（キーレス）・単語時刻・話者分離 | CER 11.5%、話者純度 97〜99%、125秒を3.9秒 | 数字表記（一万→1万）が主な差 → **漢数字と算用数字を同じ値として比較** |
| [05-llm-select](../spikes/05-llm-select.cs) | Azure OpenAI Structured Outputs | 4候補、全項目合格 | strict モードは `maxLength`/`minimum`/`maxItems` 非対応（Microsoft Learn）→ **制約はコード側で強制** |
| [06-copilot-sdk](../spikes/06-copilot-sdk.cs) | GitHub Copilot SDK × OS インストール済み CLI | 合格 | エージェントが「途中の JSON」と「訂正版」の2通を送る、尺や区間数の制約違反 → **最新の完全な JSON を抽出＋同じ検証器** |
| [07-make-long](../spikes/07-make-long.cs) | 64分の日本語テスト動画を生成（LLM 台本＋TTS） | 1,252行、64分 | 性能・長尺分割の検証用 |

テスト素材は権利の問題がないよう、すべて合成（FFmpeg のテストパターン＋Azure TTS の音声）で作っています。

## 4. E2E（実ブラウザ・実 Azure）

[ui/e2e.mjs](../ui/e2e.mjs) が OS の Microsoft Edge（ヘッドレス）でアプリを操作します。最終実行: **9/9 合格・91秒**。

## 5. E2E で見つけて直した不具合

| 発見 | 原因 | 対策と再発防止 |
|---|---|---|
| 権利確認の文が画面に出ない | Fluent v3 の `fluent-checkbox`/`fluent-switch` にはラベル用スロットがない | `fluent-field`（label / input スロット）で構成 |
| 開発用の例外画面（スタックトレース）が返る | `launchSettings.json` が Development 環境を強制 | 削除し、JSON 形式の例外ハンドラを追加 |
| 候補3のテロップが画面外へはみ出し（H-05 で検出） | 強調語に13字の「文」が入り、改行なしで描画 | 強調語は10字以内に制限、全テロップを安全幅に収まるよう自動縮小（回帰テストあり） |
| 字幕の孤立行（「…いっぱい」＋「ですよ」） | 貪欲法の改行 | 動的計画法で行幅を均等化（回帰テストあり） |
| 強調テロップ同士の重なり | 近い時刻の強調語が同じ行に重なる | 時刻順に処理し重なりを解消（回帰テストあり） |
| ステップ表示の上下が欠ける | スクロールコンテナを含む grid 行の最小高さが 0 | レイアウトを修正 |

## 6. 判断が必要な点

1. **長尺の絞り込み（NFR-COST-03）と品質のトレードオフ → v1.1 でアプリ内で選べるようになりました**。プロジェクト画面の「生成の設定」で「節約／標準／全文」を選び、各項目の「AI に送る量」と費用の目安がその場で見えます。64分の素材（`spikes/media/long.mp4`、実 Azure）での実測（ASR はキャッシュ済みのため所要は AI 選定以降）:

   | 項目 | AI に送る量 | 入力トークン | 費用（実績） | 最上位スコア | 所要 |
   |---|---|---|---|---|---|
   | 節約 | 約31%（2区間） | 12,010 | ¥62.72 | 9.06 | 66 秒 |
   | 標準（既定） | 約46%（3区間） | 18,710 | ¥63.97 | 8.52 | 85 秒 |
   | 全文 | 100% | 34,224 | ¥65.09 | 9.40 | 103 秒 |

   費用の大半は書き起こし（¥57/時間）なので差は 1 時間あたり約 ¥2〜3 です。合成音声は音量の変化が小さいため、実際の動画では絞り込みの当たり外れが変わります。見落としを減らしたいときは「全文」をおすすめします。
2. **字幕の表示速度（S-01）**: 早口の発話を全文字幕にすると毎秒6字を超える箇所が出ます（警告のみ）。FR-TEL-02 の第3段階（AI による短縮）は未実装です。

| 項目 | 実装と検証 |
|---|---|
| 早送り（P8）の実映像での確認 | NASA の実映像（パブリックドメイン、`spikes/media/rollout.webm`）に、既知の時刻で発話を重ねた 5 分の素材で検証。110 秒分の映像を 9.5 秒に圧縮（×11.6）、発話 2 か所は 1 倍速のまま、書き出しはハード QA 全合格。**書き出した動画を Azure Speech で書き起こし直すと、残した発話の文字を 100% 回収**（第三者による検証） |
| クロスフェード（FR-SWT-05） | 元映像が 3 秒を超えて飛ぶ場面転換にだけ入れる（P6 は 0.3 秒、プリセットの `scene_fade_sec`）。音声はハードカット、前のカットの映像を重なり分だけ延ばすので尺は変わらない。実フレームの色で「前→混ざる→後」と、連続する箇所は混ざらないことを確認 |
| ループの意味的接続（FR-SOL-06） | ループ有効のパターンで、終わりの位置の 5 案を LLM が冒頭の文とのつながりで採点し、最高点の案を採用（E2E で 3/3 候補に適用） |
| 字幕の AI 短縮（FR-TEL-02 第3段階） | 分割・表示延長でも毎秒6字に収まらない字幕だけ、LLM が文字を**削るだけ**で短くする。元の文字の部分列でなければコード側で却下（言い換え・数字の追加は不可。単体テストで確認） |
| 書き起こしの手修正（FR-ASR-06） | 確認・修正画面の「書き起こしを直す」で単語を修正（時刻はそのまま）。字幕が作り直され、修正はキャッシュにも保存される（E2E で確認） |
| 笑いの検出（FR-SIG-04） | 単語のない大きな音のうち、約3〜8Hz で脈打つもの（「ハハハ」）だけを笑いとする。一定の雑音（拍手のような）と単発の衝撃は除外（合成音で確認） |
| 話者とカメラの自動割り当て（FR-SWT-01） | カメラごとのマイク音声で、相対的に最も大きい話者を割り当てる。マイクが共通で判別できないときは警告し、基準=話者1、カメラB=話者2 の既定に戻して手入力で変更できる（合成音で確認） |

| 範囲 | 状態 |

## 9. 前編・後編（指定した長さのシリーズ）

長尺全体を、指定した **本数（2〜20本）** または1本あたりの長さ（1〜60分、どちらか一方）で **前編/後編**（3本なら中編、4本以上は第n話）に分け、既存パターンと同じ編集をかけます。対象は発話を軸に編集するパターン（P1〜P4・P6・P7・P9・P10）です。実装: [Series.cs](../src/VideoCreator.Core/Planning/Series.cs)、検証: [SeriesTests.cs](../tests/VideoCreator.Tests/SeriesTests.cs)、[spikes/13-series.cs](../spikes/13-series.cs)。

| 段階 | 内容 |
|---|---|
| 章分け | AI（Structured Outputs）が行番号付きの書き起こしを話題ごとに分け、各境界の「分けやすさ（前が自然に終わり、続きを見たくなるか）」・見どころの行・強調語を返す。行番号・見どころ・見出し・強調語はコードで検証（範囲外は除外、見出しの数字・固有名詞は書き起こしにあるものだけ）。AI がないときや失敗したときは TextTiling（Hearst 1997、内容語の文字バイグラムの語彙のつながり）と話題転換語で代替 |
| 本数 | 本数で指定したときはその本数ちょうど（1本あたり編集後1分未満になる本数は、上限の本数を示して受け付けない）。長さで指定したときは N = 編集後の長さ ÷ 指定の長さ（四捨五入、2本未満はエラー）。画面では、選んだ本数・長さから1本あたりの長さの目安をその場で表示（書き起こし済みなら分割と同じ計算による無音カット後の推定、まだなら元の長さと明記） |
| 分け目 |分け目の候補は文の境界だけ。「各パートの長さと均等な長さとの差の二乗」から「境界の良さ（語彙の変化・間・話題転換語・話者交代・AI の分けやすさ）」を引いた値が最小になる組み合わせを動的計画法で選ぶ。長さの許容は ±25%（入らなければ ±40% に広げ、その旨を表示）。分け目が AI の章の切れ目でも話題転換語の位置でもないとき（本数が話題の数を上回ったとき）は、どのパートの間か・時刻を警告 |
| 構成 | 各パートの冒頭にそのパート内の見どころ1文（先出し）、2本目以降は前のパートの最後の1〜3文（「前編のおさらい」）、最後以外は次のパートの先出しを「後編につづく」として最後に置く。本編は無音のジャンプカット＋パンチイン、章ごとの見出しテロップ、字幕・強調は通常のパターンと同じ |
| 網羅性 | 本編どうしは重ならず、すべての単語がちょうど1つのパートの本編に入る（おさらい・予告は意図した重複） |
| 長尺の書き出し | ①順番が入れ替わるクリップ（先出し・おさらい・予告）は、前へ進むまとまりごとに別の入力として `-ss` で正確にシークして開く（1つの入力を共有すると、先に再生するクリップのために後のクリップのフレームを溜め込むため）。②数百のクリップのフィルタグラフは Windows のコマンド長の上限（32,767 文字）を超えるため、ファイルで渡す（`-/filter_complex`）。③1つの入力を多数のクリップで使うときは `split`/`asplit` で分岐（約25% 速い）。④プレビューは半分の解像度で直接合成（テロップは ASS の PlayRes で同じ配置）。⑤安全領域の実測は、幅の広いテロップと均等に間引いた最大160件で行う |
| QA | H-01 は各パートの範囲（均等な長さの ±30%）。H-07 はシリーズ名がほかのパートの内容を指すことがあるため書き起こし全体と照合し、パートのラベル（第2話など）は事実の主張として扱わない。S-10: YouTube のチャプター条件（00:00 から・3つ以上・各10秒以上、YouTube ヘルプ「Video chapters」）。S-11: 60分以下（TikTok のアップロード上限） |
| メタデータ | タイトルに【前編】などを付け、チャプター（上の条件を満たすよう、10秒未満の章は前の章に統合）とシリーズの各パートのリンク欄を出力。縦型でも3分を超えると YouTube ではショートにならないため #Shorts は付けない |

### 検証（実動画・実 Azure、`dotnet run spikes/13-series.cs`）

素材は 64分のテスト動画（LLM の台本＋TTS）の先頭30分。台本は話題ごとに「続いての企画は…」で始まるため、その文の位置を **正解の話題の境界**（19区間）として使いました。

| 項目 | 結果 |
|---|---|
| 分け目（15分×2本） | **15:22**（正解の話題の始まりと一致、0.0秒）。比較: 時計どおり 15:00 で切ると最寄りの話題の境界から 22.8秒ずれ、**単語「今日は」の途中で切れる** |
| AI の章分け | 19章（正解 19）、**Pk 0.000 / WindowDiff 0.000** |

## 10. オープニング・クロージング・場面転換のツッコミカード

チャンネルのオープニング／クロージング動画と、場面が変わる所に入る約1秒の「ツッコミ」カードを入れます。実装: [Packaging.cs](../src/VideoCreator.Core/Planning/Packaging.cs)（写像・登録・配置）、[Renderer.cs](../src/VideoCreator.Core/Rendering/Renderer.cs)、検証: [PackagingTests.cs](../tests/VideoCreator.Tests/PackagingTests.cs)。

| 段階 | 内容 |
|---|---|
| 登録 | フォルダー（またはファイル）のフルパスを「3. 生成する」で登録（全プロジェクト共通、権利確認が必須）。ファイル名の Opening / Intro / オープニング、Closing / Ending / Outro / エンディングで判別し、判別できない動画は推測せず理由を表示。PNG / JPG はカード画像。登録時に ffprobe で解像度・尺、ebur128 で積分ラウドネスを測って保存 |
| 版の選択 | 9:16 と 16:9 の両方があれば、出力（1080×1920）に形の近い方を自動で選ぶ。形が違うときは本編と同じくぼかし背景で収める |
| 配置 | オープニングは **先出し（コールドオープン）のあと**（日本のバラエティ系の定番の順。先出しがないパターンでは先頭）。クロージングは最後。カードは、ショートでは元動画で3秒以上先へ飛ぶ本編の継ぎ目（FR-SWT-05 のクロスフェードと同じ定義。カードを入れた所はクロスフェードの代わりにカード）、シリーズでは章の頭。章の頭から4秒以内に継ぎ目がなければ、そこでクリップを分けて継ぎ目を作る（続けて話している素材でも話題の変わり目に入る）。間隔は8秒以上、本編の端から3秒以上、ショートは最大3枚 |
| カード | 直前の場面の最後のフレームを止めて少し暗くし、黄色の太字（libass、安全領域に収まるよう自動縮小・水平は安全領域の中央）か登録画像を重ね、効果音「hit」を鳴らす。文字は AI があれば直前の字幕から14字以内のツッコミを提案（ツッコミテロップと同じ検証: 禁止語・字幕にない数字や固有名詞は不可、**承認するまで書き出せない**）。AI がないときは「さて、次！」などの当たり障りのない定型文。確認画面で文字の編集・承認・個別のオン/オフ |
| 時刻 | テロップ・効果音・チャプターは本編の時刻で作り、挿入物の分だけ後ろへずらす変換を `InsertMap` の1か所に集約（ASS・SRT・効果音・BGM のミュート・チャプター・サムネイル・QA の顔検出がすべてこれを使う）。挿入物をまたぐテロップは前後に分けて、カードやオープニングの上に字幕が出ないようにする |
| 音 | オープニング・クロージングの音は、まず **本編のミックスを測って同じラウドネスに合わせて** から、ファイル全体を −14 LUFS に正規化（絶対値の −14 に合わせると、本編が正規化前に小さいため OP だけ 12 LU 大きくなることを実測で確認して直した）。BGM はオープニング・クロージングの間は止め、クロージングの頭でフェードアウト |
| フレーム精度 | クリップごとに丸めたフレーム数と、concat が映像と音声の長い方に合わせる動作で、1クリップあたり約17ms 伸びていた（25.95秒の計画が 26.10秒。数百カットのシリーズでは数秒ずれる既存の問題）。計画の **累積時刻** でフレーム数を決め、音声はサンプル数（48kHz/30fps = 1600 サンプル/フレーム）で同じ長さにそろえた。AAC の先頭のプライミング（−0.011s）で次の区間が約0.1秒遅れる問題も、リサンプル後にタイムスタンプを振り直して解消 |
| QA | H-01 はパターンの範囲を **本編** に、Shorts の 180 秒上限を **全体** に適用し、ファイルの長さが計画と一致することも確認。H-07/H-08 にカードの文字を含める。H-09 は挿入物の権利確認。S-03 はショートでオープニングが先頭にあると警告（冒頭の数秒で離脱されるため）。S-06 はカード・オープニング・クロージング内の静止を除外。S-12 は素材が出力より小さく拡大されると警告 |

### 小さいオープニング・クロージングの高画質化

登録したオープニング・クロージングが出力（1080×1920）より小さいとき（サンプルは 720×1280）、登録時に一度だけ高画質化した版を作り、書き出しではそれを使います。実装: [SuperResolution.cs](../src/VideoCreator.Core/Media/SuperResolution.cs)、[Packaging.cs](../src/VideoCreator.Core/Planning/Packaging.cs) の `BrandKitEnhancer`、[BrandKitWorker.cs](../src/VideoCreator.App/BrandKitWorker.cs)、検証: [UpscaleTests.cs](../tests/VideoCreator.Tests/UpscaleTests.cs)、[spikes/14-upscale.cs](../spikes/14-upscale.cs)。

**方式は測って決めた。** 正解のある超解像の標準的な評価として、元の 720×1280 を 2/3 に縮小し、各方式で 1.5 倍に戻して元と比べた（FFmpeg の libvmaf **NEG モデル**＝鮮鋭化で点数が上がらない版、XPSNR、SSIM。圧縮条件はそろえる）。

| 方式（オープニング） | VMAF-NEG | XPSNR-Y | SSIM | 判断 |
|---|---|---|---|---|
| lanczos（従来の書き出し時の拡大） | 92.77 | 44.29 | 0.99792 | 基準 |
| lanczos + CAS 0.4（鮮鋭化） | 94.81 | 39.86 | 0.99575 | VMAF は上がるが XPSNR −4.4 dB。元から離れる |
| spline36 | 92.33 | 44.17 | 0.99792 | 改善なし |
| libplacebo ewa_lanczossharp（GPU） | （通常の VMAF で 93.40、lanczos は 93.51） | — | 0.99686（lanczos 0.99819） | 改善なし |
| Real-ESRGAN animevideov3 単体 | 86.53 | 24.50 | 0.99275 | 文字はくっきりするが、背景のパステルのグラデーションの明るさを変えてまだらにする（差分画像で確認） |
| **lanczos ＋（モデル − lanczos）の高域 × 0.4**（採用） | **93.88** | **44.70** | **0.99794** | 3指標すべてで基準以上 |

クロージングでも同じ設定で VMAF-NEG +1.11・XPSNR +0.71 dB・SSIM +0.00007（設定を1本に合わせ込んでいないことの確認）。

| 段階 | 内容 |
|---|---|
| 仕組み | 色差と低周波（色・明るさ・グラデーション）は元の YUV から lanczos で作り、輝度の細部だけをモデル（4倍）を面積平均で縮小したものとの差分の高域（ガウス σ 0.7）から 0.4 倍で加える。RGB を経由した往復はそれだけで XPSNR −4 dB だったため、色はモデルを通さない |
| 素材ごとの採否 | 登録した動画そのものの中央4秒で上と同じ比較を行い、lanczos より忠実なとき（VMAF-NEG が下がらず、XPSNR の低下が 0.1 dB 以内）だけ採用。そうでなければ元の動画のまま使い、理由を表示 |
| 実行 | 登録後に裏で実行（画面に進み具合を表示）。ONNX Runtime の DirectML（GPU）で 720×1280 1フレーム 0.13 秒の推論（CPU は 6.3 秒）。DirectX 12 の GPU がなければ CPU に切り替え。保存は x264 CRF 10（ほぼ無劣化）、音声は無変換、フレームは全数そのまま。結果はファイルの名前・サイズ・更新時刻ごとにキャッシュし、同じファイルの再登録はすぐ終わる。キャッシュが消えていたら元の動画で書き出す |
| 表示・QA | 登録画面に「→ 1080×1920 に高画質化済み（GPU・89秒。この動画での実測: VMAF +1.1・XPSNR +0.35 dB）」。S-12 は高画質化済みなら合格、拡大のままなら警告 |
| 依存 | `Microsoft.ML.OnnxRuntime` を `Microsoft.ML.OnnxRuntime.DirectML` 1.24.4（CPU も含む）に変更。顔検出を含む既存テストはすべて合格。モデルは get-tools.ps1 が Hugging Face から取得し SHA-256 を検証（変換元 Real-ESRGAN v0.2.5.0、BSD 3-Clause） |

実装中に計測で見つけて直したもの: ①`progress?.Report(++n)` は progress が null だと `++n` ごと評価されず、正常処理を「0 フレーム」と誤判定していた。②FFmpeg が親の標準入力をキー操作として読み、デコードが即終了していた（`-nostdin`）。③推論結果の 4400 万要素のコピーと1画素ずつの変換で 0.69 秒/フレームかかっていたのを、出力先の配列を直接渡す方式と行ごとの並列化で 0.28 秒に（出力はビット単位で同一）。

実素材での結果（アプリの画面から `C:\Work\HubRadio\OpeningClosing` を登録）: オープニング 89 秒で採用（VMAF-NEG +1.1、XPSNR +0.35 dB）、クロージング 98 秒で採用（+1.3、+0.84 dB）。実収録から生成・書き出しまで通し、書き出しは高画質化版（1080×1920）を使い、ハード QA 全合格、S-12 合格。

限界: 拡大で失われた細部は戻らず、改善は VMAF で +1 前後と控えめ。最もきれいなのは、元の制作データから 1080×1920 で書き出し直した動画を登録することです。カード画像は画面の一部に縮小して重ねるため対象外です。

## 11. 複数素材の自動同期と画面解説（P10: 画面収録＋話し手のワイプ）

同じ場面を撮った複数の素材（カメラ・PC の画面収録）を、人が介在せずに **1フレーム未満** の誤差で合わせ、画面収録と話し手のカメラを自動で見分けて「画面＋話し手の円形ワイプ」と「話し手の全画面」を切り替えます。実装: [AudioSync.cs](../src/VideoCreator.Core/Audio/AudioSync.cs)、[ScreenActivity.cs](../src/VideoCreator.Core/Media/ScreenActivity.cs)、[ScreenPlanner.cs](../src/VideoCreator.Core/Planning/ScreenPlanner.cs)、[Renderer.cs](../src/VideoCreator.Core/Rendering/Renderer.cs) の `AppendScreen`、[P10.json](../presets/P10.json)。検証: [MultiSourceTests.cs](../tests/VideoCreator.Tests/MultiSourceTests.cs)。

### 同期（P7・P10 共通）

従来は「冒頭 90 秒・±20 秒の範囲で GCC-PHAT を 1 回」でした。既知のずれを入れた素材で測ると、次の 2 つを **黙って間違えて** いました。

| 素材 | 正解 | 従来 | 現在 |
|---|---|---|---|
| 基準の音声トラックが映像より 0.28 秒遅れて始まる（MP4/AAC。OBS・スマホで起こる） | +2.000 秒 | **+2.279 秒（8 フレームずれ、しかも「信頼できる」判定）** | +2.0002 秒 |
| カメラの録画開始が 35 秒遅い | −35.000 秒 | 不一致として **そのカメラを捨てる** | −34.9999 秒 |
| カメラの時計が 200 ppm 速い（150 秒） | +1.5 秒・−200 ppm | 窓の中でずれが動き判定不能 | +1.4999 秒・−209 ppm（端での誤差 1.5 ms） |
| 20 分・60 ppm（一般的なカメラ） | 終端で 72 ms ずれる | 補正なし | −62.5 ppm、終端の誤差 3.1 ms |
| 実音声（2 人の会話）、帯域制限・雑音・小音量のカメラ | +4.217 秒 | — | +4.2168 秒 |
| 無関係な音 | — | 却下 | 却下 |

| 段階 | 方法 |
|---|---|
| 時刻の基準 | PCM を `aresample=async=1:first_pts=0` で **タイムスタンプどおり** に取り出す（遅れて始まる音声は無音で埋め、途中の欠落も埋める）。サンプル i ＝ファイル時刻 i/rate となり、trim/atrim で切る時刻と一致する。書き起こし用の 16 kHz 音声も同じにした（単一素材でも字幕とカットがずれない） |
| 粗い探索 | 全長の対数エネルギー包絡（50 Hz、ストリーミングで計算し全 PCM はメモリに持たない）を GCC-PHAT で相関。ずれの探索範囲は素材の長さ全体（短い素材が長い基準の後半から始まる場合も含む） |
| 細かい探索 | 重なり全体に最大 24 の 10 秒窓（8 kHz）で GCC-PHAT、ピークは放物線補間でサンプル以下まで |
| 時計のずれ | 窓ごとのずれに Theil–Sen 直線を当て、直線から 8 ms 以内の窓だけで当て直す。重なり全体で 2 ms 未満の傾きは 0 とみなす |
| 信頼性 | ピークの高さだけでは判定しない（ドリフトがあると窓の中でピークがぼけ、高さが 14〜70 に落ちても位置は 2 ms 以内で正しいことを実測）。**3 つ以上の独立した窓が 1 本の直線に乗り、半数以上が一致** すれば採用。無関係な音のピークは直線に乗らない |
| 長いクリップ | 時計がずれる素材のクリップは、半フレーム以内に収まる長さで分けて区切りごとに基準へ合わせ直す（60 ppm なら 4.6 分ごと） |
| 音声がない素材 | 両方のファイルに撮影日時（`creation_time`）があればそれで合わせ、±1 秒程度と警告。なければ開始が同時として扱い警告（従来どおり）。手入力の「ずれ(秒)」は常に優先 |
| 表示 | 素材の欄に「音声で同期: −7300.0 ms・5/5 区間が一致（残差 0 ms）」、ドリフトがあれば「1時間で N ms を補正」（FR-ING-05） |

**第三者による検証**: 同じファイルを、本実装とは別の方法（SciPy の `scipy.signal.correlate` による通常の相互相関。タイムラインのフィルターを使わず、ffprobe のストリーム開始時刻を明示的に足す）で測り、すべて一致しました（+2.0000 / −35.0000 / −7.3000 秒、20 分素材のドリフト −62.4 ppm ＝本実装 −62.5 ppm）。BBC の audio-offset-finder は、この環境で設定されているパッケージ フィードになかったため使っていません。

### 画面収録と話し手（P10）

| 段階 | 方法 |
|---|---|
| 役割の判別 | 素材ごとにプロキシを 2 fps・640×360 の濃淡で比べ「ほぼ変化しない 0.5 秒」の割合と、6 か所 × 4 秒の顔検出率を測る。画面収録 = 静止 30% 以上で最も静か（顔は不利に数える）、話し手 = 残りで最も顔が多い素材。役割「画面（PC の画面収録）」を指定すればそれが優先。判定と根拠（例: 「presenter.mp4: 静止 1%・顔 100%、screen.mp4: 静止 82%・顔 0%」）を表示 |
| 画面の動き | 前のフレームと **2 つ前のフレームの両方** と違う画素だけを数える（点滅するカーソルや元に戻るハイライトは動きではない）。1 文字の入力（実測 19〜50 画素）を拾えるよう、しきい値は 12 画素（静止画面は 0〜2 画素）。変化の位置（8×8 ブロックの外接矩形）と、2 秒ごとの 16×9 の細かさ（輝度勾配）も保存 |
| 切り替え | 0.25 秒刻みで「画面が変化している（0.6 秒前から 1.0 秒後まで）」または「文が画面を指している（ここ・クリック・ボタン…）」なら画面。そうでない状態が 4 秒続いたら話し手の全画面。最初の 2 秒は話し手の顔（変化中を除く）。2 秒未満の区間は前後に吸収し、切り替えは近くのジャンプカットへ寄せる（画面を長く見せる方向なら 2 秒まで） |
| ズーム | 9:16 では画面全体を幅 1080 に縮めると文字が読めないため、画面の帯に合う形で、変化している所の 75 パーセンタイルの大きさ（余白 1.3 倍）を切り出す。拡大は最大 1.5 倍（それ以上は文字がぼける）。中心は変化の位置を 1 秒で平滑化・速度制限して追う（パン）。スライドの切り替えのように画面全体が変わる区間は全体を表示 |
| レイアウト | 画面の帯は見出し（上）と強調・字幕（下）の **間** に置き、テロップが画面の内容に重ならない。残りは画面のぼかし・暗くした複製。ワイプは円形・白い縁（帯の高さの 42% まで）。マスクは 1 フレームだけ geq で作ってループ（毎フレーム計算しない） |
| ワイプの位置 | 4 隅それぞれについて、ズーム・パンを逆にたどって画面上の位置に戻し、①変化している所との重なり ②細かい所（文字・UI）の量 を合計して最小の隅を選ぶ。スライドの題名や入力中の行を隠さない。話し手は顔の中央値を中心に頭と肩が入る正方形で切り出す |
| QA | H-09 の権利確認にワイプの素材も含める（ワイプの中だけに映る素材の権利漏れを防ぐ） |

### 検証

- **正解を埋め込んだ合成素材で、出力を実測**（`Screen_and_presenter_are_synced_switched_and_composited`）: 話し手のカメラ（基準）に既知の時刻の白い閃光とビープ、画面収録（2.5 秒遅れて開始、音声トラックはさらに 0.3 秒遅れて開始）に右上での入力と、ビープと同時のマゼンタの表示。書き出した動画をデコードして測り、①ビープの開始が計画どおり（±20 ms）②すべてのビープに対し、表示中の領域（全画面またはワイプ）の閃光が **1 フレーム以内** ③画面側のマーカーも 1 フレーム以内 ④画面区間ではワイプが青（話し手）・帯が灰色（画面）、話し手区間では青、を確認
- 単体: 遅れて始まる音声・35 秒遅い開始・200 ppm のドリフト・外れ値に強い直線・ドリフトでのクリップの合わせ直し・小さな文字入力は拾いカーソルの点滅は拾わない・スライドの文字を避けるワイプ・テロップと重ならない帯・シリーズ（シーク付き入力）でのワイプと音声の入力
- **実アプリでの通し**（API から、役割は指定せず、実 Azure の書き起こしと AI 選定）: 顔写真に頭の揺れとセンサー雑音を加えた話し手（音声は実際の会話）と、7.3 秒遅れて始まり音声トラックが 0.2 秒遅れる画面収録（エディターへの日本語入力 → スライド → ターミナルへのコマンド入力）。役割を正しく判別、同期 −7.300 秒（5/5 区間一致・残差 0 ms）。画面区間はエディター入力の 0.8 秒前・スライドの 2.6 秒前（既存のカットへ寄せた）・ターミナル入力の開始ちょうどから始まり、ターミナル入力中のワイプは入力行と反対側、スライドの題名は隠れない。3 候補ともハード QA 全合格
- この過程で見つけて直したもの: ①1 文字の入力が 360p では 19〜50 画素で、最初のしきい値（92 画素）では見逃していた → 12 画素＋点滅の除外。②切り替えがカットの 1.3 秒手前に来て短い断片ができていた → 画面を長くする向きにはカットへ寄せる距離を広げた。③スライドの切り替えは位置の情報がなく、ワイプが題名に重なっていた → 細かさの地図を追加。④シリーズ（前編・後編）で別カメラの音声を基準から読む入力の解決が `audio:` 付きの ID で失敗する潜在的な不具合（P7 のシリーズに影響）を修正

制約: 画面の「どこが大事か」は動きと細かさから推定しており、意味（どのボタンの説明か）は見ていません。画面収録に音声も撮影日時もない場合は開始が同時として扱うため、「ずれ(秒)」での指定が必要です。縦型（9:16）向けのレイアウトです。
